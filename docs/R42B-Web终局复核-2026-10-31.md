### 1.4 检查点上观察到的时序现象（**已按 §1.4.1 更正，不是结构性死锁**）

### 2.4 同批被找到的第二个真缺陷：RU10 恒定失败（r42c-web-endgame 发现并修复）

> 这一节不是"备查"，它是**终局墙钟 976 s → 660 s 的根因**（§1.4.2），也是规则 2 存在的理由。

**缺陷本体** `oreki-eternity-automation.js` `holdForRealityUpgrade10()` 原本写 `player.eternities > 0`。
`player.eternities` 是 Decimal，`extensions.js:232` 让 `valueOf` 直接抛
`Implicit conversion from Decimal to number` ⇒ 该函数**每帧抛异常、被 catch 吞掉、恒 false**
⇒「为现实升级 10 压住第一次永恒」这条机制**从写下来就没生效过**。

**根因链条（必须按这个顺序写，不是时序问题）：**

```
player.eternities > 0  →  Decimal.valueOf() throw  →  catch 吞掉  →  holdForRealityUpgrade10() 恒 false
    →  每个现实拿不到 RU10  →  成就 147 不成立  →  特蕾莎（Teresa）不出现
    →  Laitela 推到 tier 8 更慢  →  Pelle / GameEnd 更晚
```

**修复**（r42c 已改）：
```js
Currency.eternities.gt(0) || Number(Currency.infinityPoints.value.exponent) >= 400
```
并加 `_ru10GaveUp` 闩锁，把「压住 10 s」改成每现实最多一次
（防止修好比较后真的压死自动永恒）。

**实测证据：**

| 观测 | baseline1（修复前） | final1（修复后） |
|---|---|---|
| `errE`（eternity 模块错误通道）非空采样 | **952 / 958** | **0 / 165** |
| `ru10` 字段 | 全程 `-` | 68 s 变 `B`（已买） |
| `ruAll` / `ach147` / `teresa` | **958 条采样里全程 false** | 218 s **三者同时转 true** |
| laiTier ≥ 8 | 886.2 s | 597 s |
| GameEnd | 976 s | **660 s** |

`[静态推导]` 语义等价、无隐式转换；`[实测]` 上面整张表。

## 3. 第 4 项：嵌套对数曲线的数学性质

对象：`MachineHandler.baseIMCap`（`src/core/machines.js:77-81`）

```
cap(L) = max(L − 1000, 0)² · max(L − 100000, 1)^0.2 · 100
其中 L = log10(uncappedRM) = 3·(log10EP / 4000 − 1)        （machines.js:33-38）
```

| 性质 | 结论 | 状态 |
|---|---|---|
| 输入 | `L`（RM 的十进制指数，无量纲）；`log10EP` 是**指数**，不是 EP 本身 | `[静态推导]` |
| 输出 | IM 上限（台数，无量纲），再乘 `ImaginaryUpgrade(13)` 与 `OREKI_IM_CAP_MULT=100` | `[静态推导]` |
| 单调性 | `L>1000` 上严格单调增；`L≤1000` 恒 0。数值抽样 900→12000（步长 1）**非减，0 例外** | `[实测-数值]` |
| 连续性 | C⁰ 连续（`L=1000` 处为 0；`L=100001` 处两段都为 1 倍率）；C¹ 不连续（两处折点） | `[实测-数值]` |
| 边界 | `L≤1000`→0；`L=1000.001`→1.0e-4；`L=1e5+1`→9.8e11（第二因子从常数 1 切换为 `x^0.2`，斜率无穷大但值不跳） | `[实测-数值]` |
| 溢出 | 实际可达 `L≈1.8e4` → cap≈3.0e10，double 安全；要溢出需 `L>1e154`，不可达 | `[静态推导]` |
| 小值行为 | 二次项主导：cap ∝ (L−1000)²，`L` 每 +1 约 +0.16%（相对），前期非常"钝" | `[实测-数值]` |
| 极大值行为 | `L≤1e5+1` 时二次项主导；超过后 `L^2.2`，但该区（`log10EP≈1.33e8`）比当前 EP 天花板高一个数量级 | `[静态推导]` |
| **理论临界线（不是当前瓶颈）** | IU25 的 5e9 需 `L≥8071` ⟺ **`log10EP ≥ 1.0765e7`**；真实新档峰值 **2.43e7** ⇒ 余量 **×2.26**，实测买入时 IM 2.97e10 = 5e9 的 **×5.94** | 临界线 `[静态推导]`+数值；峰值与买入值 `[实测]`（r42c 新档） |

| log10EP | L=log10(RM) | IM cap |
|---|---|---|
| 1.0000e7 | 7497.5 | 4.22e9（< 5e9，IU25 买不到） |
| **1.0765e7** | **8071.1** | **5.000e9（IU25 临界）** |
| 1.2000e7 | 8997.0 | 6.395e9 |
| 1.4300e7（`machines.js` 注释里 R34b 的旧读数） | 10722.0 | 9.452e9 |
| **2.4300e7（r42c 新档实测峰值）** | **18222.0** | **2.966e10** |

**口径自证**：把实测峰值 `log10EP = 2.4306e7` 代进公式得 `2.966e10`，
与 r42c 控制台记录的实际买入值 `im=2.97e10` **三位有效数字吻合**
（`[R38-IU25] 已买入（tier=8 im=2.97e+10 符文=0）`）——
说明「输入是每现实 `maxEP.exponent`、输出是 `baseIMCap×100`」这条读法是对的。

**判读（已按实测更正）：**
