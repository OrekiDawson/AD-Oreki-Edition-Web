**判读：**

1. 每次现实发生的那一刻，`EternityChallenge(1..12)` **全部 5/5**。也就是说 EC 链不是「卡在 EC2」，
   而是**整个 12 关在 ~35 s 内重建完成 → DS6 到手 → 现实立刻重置 → 重来**。
2. `ts171` 在 634 个采样里 **301 个为 true**（`ec-probe` 采样 4.8 s 起即已买到），
   `ecBuyCalls=136 / ecBuyTrue=49` —— 买 EC 研究/进挑战的路径是通的。
3. `realTry=2728` 而 `realOk=4`：`shouldReality()` 每帧都在被判 false（间隔/收益），
   命中一次就立刻现实 —— 间隔实测 **~35 s**（R39 数据 2230 条里 71 次现实，中位间隔 23.7 s，
   本轮检查点更慢，35 s），不是「10~20 s」，量级一致但更慢。
4. 因此 **R39 的结论是对 1 s 采样的误读**：单点采样看到 `ecDone` 退化成 `5,0,5,0...`，
   被当成「EC2 卡住」；实际那是现实刚重置后**正在重建的中途快照**。

### 1.3 为什么 R39 的改法不成立（两层）

**第一层：`shouldHoldReset()` 零调用点。** `[静态推导]`（`rg` 穷举，`src/` 全量）

```
src/game.js:247                    export function orekiEcEntryHold() { return OrekiEternityAutomation.shouldHoldReset(); }
src/core/oreki-eternity-automation.js:468  shouldHoldReset() {...}
```

`orekiEcEntryHold` 没有任何 import 方；`shouldHoldReset` 也只在 `:468` 定义。真正接在
大坍缩自动器上的挂钩在 `big-crunch-autobuyer.js:129-137` **已被显式回退**（注释写着
「AD12 已回退 / AD14 已回退」）。所以给它加「有界准备期」= 给死代码加参数，**运行期零效果**。

**第二层：压大坍缩压不住现实。** `[静态推导]` 现实的唯一闸门是
`isRealityAvailable()`（`reality.js:119`）= `maxEP.exponent ≥ 4000 && TimeStudy.reality.isBought`，
与坍缩完全无关。要「给 EC 留窗口」只能压 `OrekiRealityAutomation.shouldReality()`（或它读的
`OrekiCelestialAutomation.holdReality`），不是压坍缩。

### 1.4 当前的真实链条（这才是下一轮该动的）

`[实测]` + `[静态推导]`：

```
① EC 链 35 s 重建到 12×5  →  ② DS6（TimeStudy.reality）到手  →  ③ 同帧内现实自动化消费掉
                                                            →  ④ game.js:903 的 endgame tick 永远看不到 DS6
```

证据：

- `ds6` 在 200 ms 采样中 **0/634 为 true**；60 ms 变化监听器全程只记录到一次 `ds6=false`（t=0.1 s），
  **没有捕获到任何一次 true** ⇒ DS6 单次存活 < 60 ms（亚帧级）。
- 而 4 次现实事件的 `pre.ds6` 全为 true ⇒ DS6 确实被买到，只是**在现实被触发前的那一帧**。
- `game.js` 调用顺序：`OrekiEternityAutomation.tick()`（:883，买 DS6）→ `OrekiRealityAutomation.tick()`（:894，现实）
  → `OrekiEndgameAutomation.tick()`（:903，IU25 判定）。IU25 的 `checkRequirement` 必需
  `TimeStudy.reality.isBought`（`imaginary-upgrades.js:362-363`），于是在同一帧被现实清空之后才判 ⇒ **恒 false**。
- 本轮 150 s 内 `iu25pos` **0/634**、`laiRun` **0/634**、`laiTier` 恒 0（`laiMaxDim` 恒 8）。

⇒ **IU25 不是「条件不够」，而是「条件成立的时刻，判定者排在清空者后面」。**

## 3. 第 4 项：嵌套对数曲线的数学性质

对象：`MachineHandler.baseIMCap`（`src/core/machines.js:77-81`）

```
cap(L) = max(L − 1000, 0)² · max(L − 100000, 1)^0.2 · 100
其中 L = log10(uncappedRM) = 3·(log10EP / 4000 − 1)        （machines.js:33-38）
```

| 性质 | 结论 | 状态 |
|---|---|---|
| 输入 | `L`（RM 的十进制指数，无量纲）；`log10EP` 是**指数**，不是 EP 本身 | `[静态推导]` |
| 输出 | IM 上限（台数，无量纲），再乘 `ImaginaryUpgrade(13)` 与 `OREKI_IM_CAP_MULT=100` | `[静态推导]` |
| 单调性 | `L>1000` 上严格单调增；`L≤1000` 恒 0。数值抽样 900→12000（步长 1）**非减，0 例外** | `[实测-数值]` |
| 连续性 | C⁰ 连续（`L=1000` 处为 0；`L=100001` 处两段都为 1 倍率）；C¹ 不连续（两处折点） | `[实测-数值]` |
| 边界 | `L≤1000`→0；`L=1000.001`→1.0e-4；`L=1e5+1`→9.8e11（第二因子从常数 1 切换为 `x^0.2`，斜率无穷大但值不跳） | `[实测-数值]` |
| 溢出 | 可达区间 `L≈1.07e4` → cap≈9.45e9，double 安全；要溢出需 `L>1e154`，不可达 | `[静态推导]` |
| 小值行为 | 二次项主导：cap ∝ (L−1000)²，`L` 每 +1 约 +0.16%（相对），前期非常"钝" | `[实测-数值]` |
| 极大值行为 | `L≤1e5+1` 时二次项主导；超过后 `L^2.2`，但该区（`log10EP≈1.33e8`）比当前 EP 天花板高一个数量级 | `[静态推导]` |
| **隐形时间墙** | IU25 的 5e9 需 `L≥8071` ⟺ **`log10EP ≥ 1.0765e7`**；实测 EP 天花板 1.43e7 ⇒ 余量仅 **33%** | `[实测-数值]` |

数值表（`node` 直接代入，可复现）：

| log10EP | L=log10(RM) | IM cap |
|---|---|---|
| 1.0000e7 | 7497.5 | 4.22e9（< 5e9，IU25 买不到） |
| **1.0765e7** | **8071.1** | **5.000e9（IU25 临界）** |
| 1.2000e7 | 8997.0 | 6.395e9 |
| 1.4300e7（实测天花板） | 10722.0 | 9.452e9 |

**判读：**

- 曲线本身**没有**引入新的隐形时间墙（单调、连续、不溢出，形状没被改动过，只做了 ×100 平移）。
- 但它把终局门槛绑在 **EP 的十进制指数**上：IU25 要求跑到 EP 天花板的 ≥75%。
  如果某次真跑的 EP 饱和在 `1.0e7` 而不是 `1.43e7`，**IU25 在数学上就不可达**，
  再多的墙钟时间也换不来 —— 这是一个应该被单独监控的量（`log10EP` 曲线），
  而不是「跑得慢」。
- 另注：`OREKI_IM_CAP_MULT=100` 是这个余量的唯一来源；若后续再调 EP 侧任何乘数，
  必须重算 `1.0765e7` 这条临界线。
