## 2. 受控 A/B 设计

单实例浏览器（**不并发**，避免后台节流），不 `GameIntervals.stop/start`，起点与操作序列完全一致：

- 起点：`infinities=1, IP=1, break=false, 16 升级清空, ipMult=0, maxAM=1.8e308`，自动购买器全开。
- 每 400 ms 执行同一套「玩家最优操作」（NC 进入、Infinity Upgrade、ipMult、间隔升级、Break、ID 解锁/买）。
- 度量窗口：`t=150s → 240s` 的 `Δlog10(maxAM)/秒`，外加终点 IP / infinities / ID1 状态。

脚本：`web/_tools/exp-microstep.mjs`（可 `OREKI_BC_MODE` / `OREKI_BC_XHIGH` / `OREKI_BUY_BI` 控制）。

## 3. 实测结果

| # | 配置 | Break 时刻 | 窗口 Δlog10(maxAM)/秒 | 终点 IP | 终点 maxAM | ID1 |
|---|---|---|---|---|---|---|
| 基线 | 微步 32，mode=0 | 120.2 s | **0.084** | 1e6.43 | 1e888 | 未解锁 |
| A | 微步 256，mode=0 | **38.7 s** | 0.030 | 1e7.46 | 1e890 | 未解锁 |
| A′ | 微步 256，X_HIGHEST×10 | 38.6 s | 0.045 | 1e7.63 | 1e892 | 未解锁 |
| B | 微步 32，X_HIGHEST×10 | 114.7 s | 0.119 | 1e6.52 | 1e932 | 未解锁 |
| C | 脚本每 400 ms 手动买满 Break Infinity 升级 | 120.0 s | 1.632* | 1e6.01 | 1e567 | 未解锁 |

\* C 的 1.632 是**度量伪影**：该窗口恰好跨过一次大坍缩，`maxAM` 被清零后从低位快速回爬，
不等于稳态推进速度。见 §4。

### 3.1 判据结论

- **实验 A（提高每帧购买阶梯处理能力）未达 3× 判据** → 假设否定。
  微步 256 反而让 Break 提前到 38.7 s（说明微步对「Break 前」有效），但 Break 之后的稳态成长没有改善。
- 因此不再走实验 B 的形式化路线（重置类改现实间隔）：B 组本身就是基线策略对照（0.119 vs 0.084），
  差异在噪声量级，且终点 IP 只差 0.09 个数量级。

## 4. 我自己的度量错误（记录，防止后续沿用）

第一次看到 1.632 时我准备当作「19.4× 突破」上报。复核后发现：

`player.records.thisInfinity.maxAM` 是**本轮无限内**的最高反物质，每次大坍缩清零。
所以「窗口内 Δlog10(maxAM)/秒」在跨坍缩时完全不可比：
- 基线组窗口末段处于**停滞段**（maxAM 长期停在 1e888），速率 0.084；
- C 组窗口恰好是**坍缩后的回爬段**，速率 1.632。

同一指标两种状态差 20 倍，属**指标失效**，不是机制差异。

**此后凡涉及本阶段，主判据改用「固定墙钟下的 IP」与「峰值 maxAM」**，
或显式区分「坍缩周期内速率」与「跨周期净推进」。

## 5. 卡点的真实形态（定点探针，175 s 快照）

脚本：`web/_tools/probe-stall.mjs`（跑完流程后一次性 dump，不连续采样）。

```
反物质=10^885   maxAM=10^885   IP=10^6.8   单次IP=10^3.9
Break=true      infinities=10^1.7   F=10000
大坍缩自动器: {mode:2, xHighest:10, interval:100, lastTick:174925.9, active:true}
提升=31    星系=6
Tickspeed=10^-61.3（其下一级成本 10^903）
AD1 产量/秒 = 10^880.3

AD1: bought 1340 / amount 1e744.9 / 下次成本 1e899
AD2: bought 1070 / amount 1e625.1 / 下次成本 1e895
AD3: bought  900 / amount 1e511.5 / 下次成本 1e889
AD4: bought  790 / amount 1e401.9 / 下次成本 1e886
AD5: bought  650 / amount 1e297.5 / 下次成本 1e907
AD6: bought  550 / amount 1e196.7 / 下次成本 1e888
AD7: bought  490 / amount 1e98.2  / 下次成本 1e906
AD8: bought  410 / amount 1e2.6   / 下次成本 1e892
```

**这是一个自洽的停滞点，不是死锁：**

1. 存量 1e885，每秒产量 1e880（≈ 存量的 1/10⁵）→ 每现实秒只增加存量的 10% 左右，
   `log10` 增速 ≈ 0.04~0.1/秒，与实测吻合。
2. 下一次能推进的购买，成本都在 **1e886 ~ 1e907**，即还差 1~22 个数量级；
   按 0.1/秒 计，单步 10~220 秒，全程到 ID1（需 maxAM 1e2695）约 **5 小时**。
3. 维度提升卡在 31（下一级需 AD8 ≥ 485，实有 410），星系卡在 6 —— **提升链也被 AD8 数量卡住**，
   于是「产量 → 买维度 → 提升 → 产量」的反馈环断开，只剩线性累积。

已排除的三条（均有实测/源码证据）：
- 生产上限：`cappedProductionInNormalChallenges` 运行时读到 `10^9.0e15`，**远未触及**；
- 公式差异：ID/Eternity/big-crunch 与 `web/upstream/official` 逐字节一致，ID 成本表全同；
- 坍缩策略：AU4b 在 `isUnlocked` 里已把 `mode==AMOUNT && amount<10` 归一化为 `X_HIGHEST×10`，
  本轮 mode=0 与 mode=2 结果几乎一致，说明它不是变量。

## 6. 本轮未交付机制改动的理由

做过但**已还原**的改动：
- `MICRO_STEP_MAX: 32 → 256`：Break 提前（120→38.7 s），但稳态成长不变（0.030 < 0.084）→ 不采用。
- 新增 `src/core/oreki-autobuy-break-infinity.js`（AU6，自动买 Break Infinity 升级）并接入主循环：
  峰值 maxAM 888 → 932（+44 数量级）、IP +0.09 数量级，**未达 3× 判据，且原判定基于失效指标** → 已 `git checkout` 还原，模块文件已删除。

> 这两项都在本机跑过真实浏览器验证，不是纸面分析。按「不发布未验证/未证明有效的机制改动」处理。

**Android AU4c 同样未实施**：`isActive` 根因已由 REA 定案，但「一次性启用且尊重玩家后续关闭」
需要新状态或精确的一次性条件；在没有 AVD 验证窗口的情况下强行改 smali 并出包，风险高于收益。
`release/反物质维度.apk` 保持 `113d871d…`，云端三处未触碰。
