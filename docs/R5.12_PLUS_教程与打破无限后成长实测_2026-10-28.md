## 2. Break → ID → Eternity 实测

### 2.1 脚本

`web/_tools/verify-id-to-eternity.mjs`（新增）：从「刚完成首次无限」出发，
跑完 16 次无限 → NC10/11/12 → 16 非重复升级 + ipMult → 间隔拉满 → Break → 解锁/购买 ID1–8 → Eternity，
逐 5 s 采样并记录墙钟。辅助诊断脚本：`diag-break-climb.mjs`、`diag-cap.mjs`、`diag-galaxy-ab.mjs`。

> 必须用 `NODE_OPTIONS="--import=file:///…/web/_tools/lib/patch-launch.mjs"` 启动，
> 否则 Edge 无头直启报 `Failed to launch the browser process: Code: 0`（本机既存环境问题）。

### 2.2 实测时间线（单实例，170 s 窗口）

| 秒 | 事件 |
|---|---|
| ~112.6 | 16 个非重复 Infinity Upgrade 买齐 |
| ~115.4 | 大坍缩自动器间隔拉满（100），随后 Break Infinity 成功 |
| 170 | maxAM=1e597.0，IP=1.41e6，infinities=52，**ID 全部 0（未解锁）** |

采样（每 5 s）：

```
t= 150.4s IP=8.82e4  maxAM=10^567.8 单次IP=10^2.9 inf=52 升级=17 ipMult=6 间隔=100 Break=Y ID=[全 0]
t= 161.4s IP=8.53e5  maxAM=10^568.3 ...
t= 169.6s IP=1.41e6  maxAM=10^597.0 ...
```

→ **maxAM 增速 ≈ 1.5 个数量级/秒**，IP 随 maxAM 同步（`10^(log10(maxAM)/308 − 0.75) × totalIPMult`，本测 totalIPMult=64）。

### 2.3 600 s 长跑的两次观测与「死锁」判定更正

第一次 600 s 长跑（**与另一次浏览器实测并发**）尾部出现 maxAM 冻结在 `1e864.6`、infinities 冻结 53、IP 冻结 5.07e5，
30 s 内无任何变化。**该现象未能在单实例复现**（§2.2 中同样区间 maxAM 稳定爬升），
因此判定为 **并发浏览器 / 后台定时器节流导致的测量污染，不是游戏死锁** —— 此结论不可作为缺陷依据。

> 记录这条是为了防止后续会话把它当成真 bug 去改代码。

### 2.4 为什么慢：把三个候选原因逐一排除

| 候选原因 | 证据 | 结论 |
|---|---|---|
| 生产上限 1.79e308/s 卡住 | 运行时读 `cappedProductionInNormalChallenges` = `10^9.0e15`（`Decimal.MAX_VALUE` 在本工程并非 1.79e308），**上限压根没被触及** | ❌ 排除（更正历史推断） |
| 公式与本项目不同 | `src/core/dimensions/infinity-dimension.js`、`eternity.js`、`big-crunch.js` 与 `web/upstream/official` 对应文件**逐字节一致**；ID 表 baseCost `[1e8,1e9,1e10,1e20,1e140,1e200,1e250,1e280]`、costMult `1e3…1e30`、powerMult `50,30,10,5,5,5,5,5` 全同 | ❌ 排除 |
| 重置类自动器把反物质掐死 | 把 `galaxy`/`dimBoost` 关掉后，全链在 1e45 就再也上不去（到不了无限）；打开时能 Break，但 maxAM 只有 1e250~1e600 量级 | ❌ 不是「关掉就好」，是**两面都受限** |

剩下的解释（**推断，未直接测量**）：`IntervaledAutobuyerState.effectiveInterval = interval / getGlobalSpeedFactor()`
对**所有**购买器生效（`src/core/autobuyers/autobuyer.js:117-119`）。F=10000 时
维度提升 4000ms→0.4ms、星系 20000ms→2ms，都小于一帧，于是**它们每帧只执行一次购买/一次重置**。
游戏时间每帧推进约 200 游戏秒，但「购买阶梯」每帧只能爬一格 —— 所以 F 从 100 提到 10000，
这段的现实时间几乎不再缩短。这与历史上「Android 主循环 CPU 受限、微步上限 32」是同一类限制。

**这不是原版缺陷**（原版速度上限远低于 10000，且原版玩家会手动控制重置时机），
但它确实是本 Mod 里**唯一还没被削掉的时间墙**。

### 2.5 本轮未改 Web 机制代码

理由：§2.4 的「购买阶梯粒度」是推断，直接改微步数/重置间隔属于平衡变更，需要先有一次能证明
「提高每帧购买次数 → 数量级/秒显著上升」的对照实验。本轮时间用于交付教程与 Android 取证，
不把未验证的平衡改动写进生产代码。

## 3. Android 自动 Big Crunch 根因（REA，本轮真实调用）

### 3.1 REA 调用记录

```
bash scripts/rea.sh doctor
  → RC=0；jadx provider ok=true；jar = tools/rea/jadx-headless-mcp-0.7.1-all.jar
  → Hopper/Ghidra/IDA 缺失（本仓库只做 JVM APK 分析，不影响）

bash scripts/rea.sh inspect-android-method "release/反物质维度.apk" \
     "kajfosz.antimatterdimensions.prestige.CrunchAutobuyerState" "c"
  → 五重 AND 短路：b() && g() && (mode判定) && (interval判定) && (amount判定)
  → 第三项 g() 已被 [Oreki AU4] 放宽，第一项 b()（isActive）未动
```

目标 APK：`release/反物质维度.apk`，SHA-256 `113d871d47a9260a8a4d956648dfe4945709b23bed1341bb2597fe39530d79f9`（69,732,894 B）。

### 3.2 根因（静态事实 + 运行证据）

1. `IntervaledAutobuyerState.c()` 的五重 AND 中，**第一项 `b()` 读 `player.auto.bigCrunch.isActive`**。
2. 15 份真实存档实测：`isActive=false` 占 **4/4**（含 `infinities=254 / IP=1e621` 的晚期档）。
   → 原版玩家普遍**从未手动打开**大坍缩自动器。
3. 短路求值先判 `b()`，为 false 时 `g()`（AU4 放宽的那一项）**根本不会被求值**，
   后面的 `tick()` / `lastTick=` 也就永不执行 → `lastTick` 恒为 0。
4. 所以 **AU4 补丁位置没错，但不够深**：它放宽了第三道门，而第一道门始终关着。

### 3.3 与历史「`prestige/e;->b` 语义未定」的关系

`a.smali` 的 `Game.autoBuyerTick` 里 `prestige/e;->b` + `MainActivity.on` 分支是**协程调度**分支，
与 `isActive` 是两回事。本轮结论不需要先解释该字段就能定案 —— 但若要继续排查「自动器在后台是否真的跑」，
该字段仍需单独核验（**未确认**）。
