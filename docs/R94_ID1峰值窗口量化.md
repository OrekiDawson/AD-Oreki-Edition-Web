# R94 Web：首次无限 → 首次永恒「ID1 峰值窗口」量化与结论

- 日期：2026-11-07（R94 第二 Web 专项）
- 范围：Web `AD-Oreki-Edition`；本文件是**分析结论 + 证据**，不是规则
- 结论先行：**窗口真实存在，但它是设计必需且不可安全提速**；本轮**未改任何生产代码/数值/门槛**。
  该阶段在 10000× 下由「两个受统一节拍约束的真动作 + 亚秒～数秒的自然峰值爬升」构成，
  推导上界约 20～25 秒，占 180 分钟目标 < 0.25%。可继续压缩的部分只剩用户明令的全局节拍本身。

  另修一处**玩家可见缺陷**（本轮同批 Web 改动的未同步项）：教程附录 F 第 1/2 章仍写「每帧固定顺序：
  买计数频率 → 维度提升 → 星系 → 维度」与「每帧处理」，既和本轮已改写的第 1/2 章正文矛盾，
  也与 `src/game.js` 的真实出手顺序、默认 10 秒统一节拍矛盾；已同步并加机器守卫。

## 2. 为什么是设计必需（不能靠「取消 HOLD」提速）

- 大坍缩会把**当前**反物质清零（`big-crunch.js` 的重置链），而 ID1 的反物质门槛读的是
  `thisEternity.maxAM`（历史峰值）。峰值只有在「当前反物质超过历史最高」时才会继续增长。
- 因此若在峰值爬升期间照常坍缩：当前反物质被反复清零 → 峰值停在最后一次坍缩时的量级（≈1e308 附近）
  → 永远到不了 1e1100。这与 `big-crunch-autobuyer.js:140-143` 的设计注释一致。
- 反过来的风险（HOLD 永不解除）已被排除：峰值指标连续更新（事实 4），门槛一到即释放（事实 3）；
  ID1 一旦解锁也立即释放（`big-crunch-autobuyer.js:178`）。
- 无旁路：全仓库 `bigCrunchResetRequest` 调用点只有 7 个文件，其中 MOD 只占两处，
  且分别被 `!player.break`（`src/game.js:386`）与 `if (player.break) return;`
  （`src/core/oreki-endgame-automation.js:821-830`）挡住；自动器本体受 `willInfinity` 门控
  （`:188-191`）。新增任何 MOD 强制坍缩路径都会让夹具第 13 项失败。

## 3. 三个提速候选的逐一否决

### 3.1 「窗口内让智能调度优先推进能提高 maxAM 的动作（提升/星系/维度/计数频率）」

**不适用。** 窗口内的峰值爬升不是 MOD 决定的：

- 原版自动购买器在首次无限后就解锁了（`antimatter-dimension-autobuyer.js:34-39`、
  `dimboost-autobuyer.js:19-24`、`galaxy-autobuyer.js:15-20` 的 `[Oreki AU2/AU3]`
  `canBeUpgraded || PlayerProgress.infinityUnlocked()`），且默认 `isActive: true`
  （`src/core/player.js:92-145`）。
- 它们的有效间隔按**游戏时间**缩放：`effectiveInterval = interval / max(1, getGlobalSpeedFactor())`
  （`src/core/autobuyers/autobuyer.js:106-123`）。默认 F=10000 时：
  维度提升 `4000ms→0.4ms`、星系 `20000ms→2ms`、反物质维度 `500~1200ms→0.05~0.12ms`。
- 这些购买器在帧内**微步**里被多次调用（`src/game.js:989-1004`、微步参数 `:1220-1229`，
  最多 32 步/帧），即 10000× 下每帧内可触发多次，远密于 MOD 的 10 秒节拍。

⇒ 峰值爬升的速率由原版自动购买器 + AD4（重置保留反物质）决定，MOD 的优先级排序
不影响这一段。夹具第 17~18 项把上述数值关系变成可回归的断言。

### 3.2 「峰值增长停滞时给出更强的增益路径」

**不适用（无剩余合法手段）。** 现存合法增益已经全部在用：

- AD4：维度提升 / 星系重置保留反物质（`docs/SHARED_GAMEPLAY_STANDARD` 平台章 + 教程附录 F 第二十一节）；
- R92：单次调度动作内买光当前买得起的提升 / 星系（`src/game.js:328-356, 394-445`）；
- R93：计数频率购买排在重置之后（`src/game.js:318-327`）；
- R91/R82：`early` 在首次永恒前可插队（只改尝试顺序，`src/game.js:1067-1082`）。

再要"更强"就只能改原版成本/门槛或伪造资源，属明确禁止；本轮不做。

### 3.3 「缩短停摆本身」

停摆内**只有两个真动作**受统一节拍限制：

1. `early`（`OrekiEarlyAutomation.tick()`）→ `InfinityDimensions.buyMax()` 解锁并买 ID1
   （`oreki-early-automation.js:83-93`，`infinity-dimension.js:397-409`）；
2. `eternityReset`（`OrekiEternityAutomation.tickEternity()`）→ 触发首次永恒
   （`oreki-eternity-automation.js:643-669`；门槛 `Player.canEternity` = IP 1.797e308，
   `player.js:971-975`）。

两者都注册在同一个调度器里（`src/game.js:1083-1098`），受**同一个全局节拍**约束
（`oreki-smart-executor.js:872-968`：`frameActed` 同帧唯一 + `lastBeatAt` 全局间隔 +
`early` 只能靠 `priorityHint` 提前尝试，且 R91 起「不得连续两拍优先」）。
默认间隔 10 s ⇒ 该阶段墙钟上界 ≈ **2 拍（20 s）+ 亚秒～数秒的自然爬升**。

要把这段再压短，只能让 MOD 动作绕过 2026-11-01 的全局单节拍用户令
（`src/game.js:1055-1066`、`oreki-smart-executor.js:882-923` 记录了该令与"删除 cont 豁免"的裁决）。
那是用户级语义变更，不是本专项可自行决定的范围。

### 3.4 关于「窗口内重复买 IP 升级」的实际情况

夹具第 20 项给出真实行为：

- 余额**恰好**等于门槛（1e8）时，任何扣费都会跌破预留 ⇒ `OrekiEarlyAutomation.hasRealWork()` 为假
  ⇒ 不申请优先拍，节拍让给 `routine`。这正是「不重复买 IP 升级」的期望行为。
- 余额**高于**门槛时，`early` 会买"买完仍 ≥ 1e8"的升级（两条购买路径都过
  `leavesId1Reserve`，共 2 处）。这些升级不会破坏 ID1 门槛，
  且首次成本 = IP 门槛 = 1e8（事实 3）⇒ 预留额度恰好保证「解锁后能买下第一层 ID1」。
  ⇒ 这里不存在需要修的浪费。

## 7. 下一轮最值得做的一件事

本轮结论把「ID1 峰值窗口」从待修瓶颈清单里划掉。**真正有量级证据的下一堵墙在开局
（首次无限之前）**，不在本阶段：

- `src/game.js:301-391` 的 `tryOrekiEarlyRoutine()`（开局唯一的购买自动化）受全局节拍限制，
  默认 10 s 一次；此时原版维度/提升/星系自动购买器**尚未解锁**
  （`isUnlocked` 依赖首次无限），所以开局没有任何"每帧级"采购。
- 间接证据：R94 本地新档探针（桌面 headless，`reports/_r94/early-*.jsonl`）
  在 ~159 s 时 `maxAM` 仅 1e96、维度提升 10，且 `served.routine` 恰为 16 次（≈每 10 s 一次）；
  而 R78 之前的 R45 基线是 4.2 s 破无限。两者的差别正是「每帧采购」vs「10 s 一拍」。
  （注意：该探针同时受 headless 帧率影响，只能作方向性证据，不能当作精确墙钟。）
- 这条要么调整"全局节拍 vs 开局采购密度"的用户级语义，要么给开局例程开一条
  有上限、可回滚、仍然"一次真动作"的例外。**两者都超出本专项授权，需要主 Agent/用户裁决。**
