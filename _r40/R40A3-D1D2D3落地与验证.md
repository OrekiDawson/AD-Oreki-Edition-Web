## 3. D1 为什么被回滚（两次真跑证据，请勿再加）

### 3.1 v1：判据 = `EC11 && EC12 都已 5/5`

`_tools/_r40/r40a3-d1v1-rejected.{log,jsonl}`（跑到 118 s 主动停）：

```
[FIRST] dilUnl t=23.6s
[FIRST] ds1   t=23.6s
（ds2~ds6 一次都没有出现）
resets: 25, 50, 75, 103   ← 每 ~26 s 一轮现实，但什么都没留下
```

**机制**：`[FIRST] ds1` 说明 EC11/EC12 一满、DS1 立刻买上，而 DS6 还要再等
`231~234 + TT ≥ 12900` 约 1.5 s。这 1.5 s 里 `chainDone` 已经为真 → 放手 → 现实把整棵研究树清空 ⇒ **DS6 永远买不上**。

### 3.2 v2：判据 = `TimeStudy.reality.isBought`（DS6 已到手）

`_tools/_r40/r40a3-d1v2-rejected.{log,jsonl}`（跑到 695 s 主动停）：

- DS6 保住了（`[FIRST] ds6 t=380 s`），`realities=60` 提前到 **349 s**（第 12 次现实的时刻，基线 446.5 s，省 97.5 s）
- **但 V 解不开**：695 s 时 `Vunl=false`、`realities=90`
- 旁路只读采样（`_tools/_r40/vprobe.mjs`，`node _r40/vprobe.mjs 9374`）直接给出六项 progress：

```
realities=1.417  eternities=10.772  infinities=0.063   ← 卡这里
dilatedTime=0.000（当时本现实 maxDT=0）  replicanti=...  realityMachines=...
infinitiesTotal = 1e121.29，要求 1e160
```

**根因（这是本次最重要的负面结论）**：
>`realities` 之前的那些「白压」不是纯浪费 —— 它们同时是**每个现实内攒产能的窗口**。
>V 的六项里 `maxDT`（1e30）、`maxReplicanti`（1e20000）都是 `records.thisReality.*`，**每现实清零**；
>`infinitiesTotal`（1e160）要靠现实内的高产出来推。
>放手太勤 ⇒ 20 s 一轮现实 ⇒ 产能记录永远长不起来 ⇒ **V 的其余五项反而永远不达标**。
>基线之所以 484.5 s 就能 V=1，正是因为它每轮压 20~45 s，给了这些 per-reality 记录长大的时间。

因此代码里现在的注释写的是「**要动只能动冷却（D2）与达标后立刻放手，不能动门槛前是否压（D1）**」。

### 5.1 最后一堵墙：反物质指数硬停在 308，`endState` 天花板 ≈ 0.75

**【实测】`r40a3-fix2.jsonl`，佩勒段逐采样：**

| t | endState | `player.antimatter.exponent` |
|---|---|---|
| 714.1 s | 0.0000 | 2 |
| 744.1 s | 0.5818 | 32 |
| 774.0 s | 0.7037 | 126 |
| 804.0 s | **0.7505** | **308** |
| 834 / 864 / 894 / 899.5 s | **0.7505（一动不动）** | **308（96 s 零增长）** |

**【静态】**`celestials/pelle/game-end.js:63-68`：
`endState = (log10(log10(totalAM)+1) − 1) / (log10(1001) − 1)`，`endState >= 1 ⟺ E >= 1000`
（`OREKI_PELLE_END_TARGET_EXP = 1e3`，`:60`）。

⇒ 若 `E = log10(AM)` 真的卡在 308，代入得 `endState_max = (log10(309) − 1) / 2.0004 ≈ 0.7448`，
**与实测的 0.7505 同量级但差 0.006**。

> **【R40-A4 复核，2026-10-30 21:0x】** 这 0.006 的差不是噪声，它指向**更准确的一层**：
> `records.totalAntimatter` 记录的是「每帧加到反物质里的那一坨」，而不是被 `dropTo` 夹住后的 `player.antimatter`。
> 未 Break 时单帧产量上限是 `DC.E315`（`antimatter-dimension.js:580-586`、`:609`），所以 `totalAM` 能到 ~1e315 附近，
> 反解 `0.7505` 得 `1e316.2`（见 `R40A4-佩勒诊断.md` §1 E5）。
> 结论不变、而且更硬：**天花板来自 `!player.break`，不是来自任何「反物质数值上限」**；
> 但「AM 卡在 308」只是 `player.antimatter` 的现值，`endState` 实际吃的是 `totalAM` 的 1e315 封顶。

**为什么是 308？—— 溯源到「佩勒里 `player.break` 恒为 false」这条静态链（与 308 精确吻合）**

| 环节 | 事实 | 出处 |
|---|---|---|
| ① 每次现实都把 Break 清掉 | `player.break = false;` | 【静态】`reality.js:633`（`eternity.js:111` 同） |
| ② 自动 Break 被显式排除在佩勒之外 | `if (!player.break && ... && !Pelle.isDoomed) breakInfinity();` | 【静态】`game.js:203-215` |
| ③ 未 Break 时维度买不过 1.8e308 | `if (!player.break && this.cost.gt(Decimal.NUMBER_MAX_VALUE)) return false;` | 【静态】`dimensions/antimatter-dimension.js:523 / :531` |
| ④ 未 Break 时大坍缩门槛就是 1.8e308 | `const hasBigCrunchGoal = !player.break \|\| ...` | 【静态】`antimatter-dimension.js:662`、`big-crunch-autobuyer.js:19`（注释：「AMOUNT 策略会把反物质永久卡在 1.8e308」） |
| ⑤ 结果 | AM 指数 = **308**（= log10 1.8e308），96 s 零增长 | 【实测】见上表 |

⇒ **这不是数值上限**：`modules/break_infinity.js:46` `EXP_LIMIT = 9e15`，`Decimal.MAX_VALUE = 1e9e15`，
比 1e308 高 13 个数量级，**库本身完全撑得住 1e1000**。
所以**不能**用「把 `OREKI_PELLE_END_TARGET_EXP` 降到 3e2」来收尾 —— 那是把「卡死」当成「通关」。

**最小修法（一行守卫）**：`game.js:211` 的 `&& !Pelle.isDoomed` 是本轮之前为了「佩勒里别自动 Break」加的，
但它同时把整局通关封死了。建议改成「佩勒里也要 Break 一次」：

```js
// [R40-A3] 佩勒阶段同样必须 Break：reality.js:633 每次现实都清 player.break，
// 不 Break 时 antimatter-dimension.js:523/531 禁止买 cost > 1.8e308 的维度、
// 大坍缩又在 1.8e308 处反复重置 ⇒ 反物质指数硬停 308
// （实测 r40a3-fix2：804~900 s 恒定 308，endState 卡 0.7505，while 目标 E>=1000）。
if (!player.break &&
  player.auto.autobuyersOn &&
  Autobuyer.bigCrunch.hasMaxedInterval &&
  !NormalChallenge.isRunning && !InfinityChallenge.isRunning && !EternityChallenge.isRunning) {
  breakInfinity();
  return true;
}
```
`breakInfinity()` 是**开关**（`player.break = !player.break`，`game.js:99`），所以必须保留 `!player.break` 守卫；
它第一行还要求 `Autobuyer.bigCrunch.hasMaxedInterval`、且 `InfinityChallenge.isRunning` 时直接 return，
不会绕过任何前置。

**【未知】**：Break 之后佩勒里大坍缩的收益形态会变（`big-crunch.js` 的 post-break 分支），
`_stopDoomedResets()` 关掉的自动器与它的交互需要一次真跑复核；**我还没有验证这条修法能通关**，
只验证到「不修就一定通不了」。

> **【R40-A4 更正，2026-10-30 21:0x】** 上面「一行守卫就够」的说法**不完整**，请以 `R40A4-佩勒诊断.md` §8 为准：
