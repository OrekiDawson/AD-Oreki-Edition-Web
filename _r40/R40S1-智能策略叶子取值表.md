## 2. 四个有坑的叶子（实现时必须照这个写，否则两端会分叉）

### 2.1 `player.infinities` —— 不是单调量

`finishProcessReality` 里有 `Currency.infinities.reset()`（`reality.js:620`），
所以「无限次数 ≥ 16」这种条件在现实之后会**重新变假**。
这是原版语义，不要为了让条件「看起来合理」而改成历史累计。
**后果**：用它的条件不能当「已达成过」用，只能当「当前这一轮有多少」。

### 2.2 `reality.shards` —— 非毁灭态恒 0

碎片只在这里加：`pelle.js:162-167` 的 `Pelle.gameLoop()`，整个方法体包在
`if (this.isDoomed)` 里。所以非毁灭态读它是 0。
**后果**：`reality.shards < 5e6` 这种条件在非毁灭态**恒为真**，不能拿它当「碎片不够」的告警。

### 2.3 `autobuyer.bigCrunchMaxedInterval` —— 不含 `autobuyerSpeed` 的 /2

`hasMaxedInterval` 读的是 `this.data.interval <= 100`（`autobuyer.js:165-167`），
而 getter `interval` 才会除以 2（`BreakInfinityUpgrade.autobuyerSpeed` 已买时）。
**结论**：这个叶子回答的是「15 级间隔升级买满了没有」，不是「实际间隔是不是 50/100」。
文案里不要写成「间隔已到 100 ms」。

### 2.4 `pelle.keepAutobuyersBought` —— 「已买」≠「已生效」

`isBought` 是 set 成员判断（`game-mechanics/set-purchasable.js:12-14`），
`canBeApplied` 才是「效果真的在起作用」（`game-mechanics/effect.js:133-135` → `isEffectActive && isEffectConditionSatisfied`）。
未毁灭态两者可能不同。
**实现**：叶子名是 `Bought`，就老实返回 `isBought`；要判「保住了自动器」得另开叶子（需先登记进 JSON）。

## 3. 两个需要 team-lead 确认的语义歧义

### 3.1 `pelle.armageddonUnlocked`

spec 里的名字是「armageddon **Unlocked**」，源码里没有这个概念，最接近的有两个：

| 候选 | 表达式 | 含义 |
|---|---|---|
| A（我采用） | `Pelle.canArmageddon` | 大灾变按钮**现在可按**（`remnantsGain >= 1`） |
| B | `Pelle.isDoomed` | 已经进了毁灭态 |

差别：末日态里刚重置完的那几秒 `remnantsGain` 可能 <1，A 会短暂为 false，B 恒真。
我按 A 实现，因为 spec 的 `blockers.shardsTooLow.advice` 明确要求「不要停掉末日循环」，
用 B 会让「能不能末日」永远为真、失去判据意义。
**如果这条与你本意不符，改 JSON 里这条叶子名（如 `pelle.canArmageddon`）更安全，别在两端各自解释。**

### 3.2 `goals[].done` 与 `blockers[].detect` 里有字符串

- `goals.finish-current-challenge.done`：`"挑战自身的完成判据（由执行层读取原版状态，不在本文件重复定义）"`
- `goals.reach-end-state.done`：`"GameEnd.endState >= 1（判据唯一来源 src/core/celestials/pelle/game-end.js:60，目标 E = 1000）"`
- `blockers.shardsTooLow.detect`：`"末日态下 realityShards < 5e6"`
- `blockers.challengeRewardMissing.detect`：`"由执行层读取原版解锁判据"`

**约定（两端都要照此）**：字符串条件 = 「无法判定」，解释器返回 `null`，界面显示「无法估算」，
**不许**猜 true/false，也不许在代码里给它们写一条等价的硬编码规则（那就等于第二份策略源）。
其中 `blockers.shardsTooLow` 那条其实是可结构化的，建议 team-lead 改成
`{"all":[{"leaf":"pelle.doomed"},{"leaf":"reality.shards","op":"lt","value":5000000}]}`。

## 4. 解释器必须实现的三条（来自 spec.conventions，不是我的发明）

| 约定 | 落地要求 |
|---|---|
| `evaluationPeriod` | 默认 1 s 求值一次；**状态变化立即重算**。建议用 8 位指纹做变化检测：`infinityUnlocked/eternityUnlocked/realityUnlocked/normalRunning/infinityRunning/eternityRunning/doomed/break` |
| `manualOverride` | 玩家手动操作后 60 s 内**该 goal** 不被自动策略覆盖；**按 goal 分域，不是全局暂停** |
| `failSafe` | 任一条件求值抛错 ⇒ 策略层整体停机，回落到 `lastKnownGoodStrategy`，禁止把异常抛到主循环 |

补充一条我加的（不是 spec 要求，但两端都建议照做）：
**未知叶子 / 未知算子 / 未知条件形状一律抛错，不要静默返回 false。**
理由：静默 false 会让自动化长期不动作，比停机更难发现；
而 failSafe 已经把「抛错」的后果限制成「回落到上次决策」，是安全的。

## 5. 分层红线（team-lead 定的，写在这里防止以后被合并掉）

- **路由层**（解释器）只产出决策对象：阶段 / 目标 / 策略 / 优先级动作 id 数组 / 阻碍项 / 手动保护。
  它**不出现任何购买 API 的名字**。
- **执行层**是唯一允许调购买 API 的地方，并且要能拒绝「当前阶段不在这个策略里」的动作。
- 两个模块不许互相写对方的字段；执行层不许反推策略（例如「我觉得该买维度了」）。

## 6. 已实测过的边界（来自 R40-A5，写在这里省得重复踩）

- `pelle.doomed == true` 的第一帧，`Autobuyer.reset()` 会把大坍缩间隔打回 150000，
  此时 `autobuyer.bigCrunchMaxedInterval` 由 true 变 false —— 条件是**会反向翻转**的，
  解释器不能假设它单调（实测 `r40a5-arm2` t=735.1 `true` → t=736.1 `false`）。
- 同一次末日会同时改变 `player.break`（true→false）、`pelle.doomed`、`reality.shards`、
  `pelle.keepAutobuyersBought` 的可用性。**末日那一帧必须强制重算**，否则 1 s 节流会读到半新半旧的组合。

## 7. 自测发现的三处问题（`node _tools/_r40/r40s1-interp-selftest.mjs`，26/26 通过）

写自测的价值就在这三条 —— 都是**静态读代码看不出来**的：

### 7.1 我自己的 bug：`gt / lt / lte` 比错了对象（已修）

第一版写成 `lt: (a, b) => cmp(a) < 0` —— `cmp` 只拿到一个参数，于是拿 `a` 和 `undefined`（→0）比，
`shards lt 5e6` 在 `shards = 1e6` 时返回 false。`gte` 因为多写了一个 `cmp(a) >= 0 &&` 的前缀反而「碰巧」对。
**教训**：比较算子必须一次性写成 `cmp(a, b)`，多算子共用一份实现，不要各写各的。

### 7.2 我自己的 bug：failSafe 有一个洞（已修）

`evaluate()` 里 `stateSignature()` 原来写在 `try` 外面。只要任一全局读取抛错
（现实里就是某个模块在初始化期半可用），异常会**直接飞给主循环**，failSafe 完全绕过。
现在指纹计算单独包一层 try，失败时用 `sig-error:<msg>` 参与比较，保证仍然走完整条 try/catch。

### 7.3 spec 缺陷：`stages` 没有优先级，`infinity` 与 `challenges` 会同时成立

未永恒、且正在跑普通挑战时：

- `infinity.detect` = `all[infinityUnlocked, !eternityUnlocked]` → 真
- `challenges.detect` = `any[normalRunning, infinityRunning]` → 真

spec 只给了数组顺序，没给 `precedence`。**两端如果一边取「第一个匹配」、一边取「最后一个匹配」，
同一个存档会判成不同阶段**，这是最隐蔽的分叉。
Web 侧按「数组第一个匹配」实现（唯一不含额外政策的确定性语义）。
建议 spec 二选一：加 `precedence` 字段，或把 `challenges` / `timeStudy` 这两个「打断型」阶段排到前面。
