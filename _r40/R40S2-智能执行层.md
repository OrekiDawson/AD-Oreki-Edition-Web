## 2. 购买权边界：选 B，理由（也写进了头注释）

三选一：

| 方案 | 含义 | 判决 |
|---|---|---|
| A | 各阶段模块让权，执行层统一买 | 否 |
| **B** | **执行层只在「该模块本帧无动作」时动手** | **选这个** |
| C | 两层并行各买各的 | 否 |

- **否决 A**：现有 6 个阶段模块是**实测能通关的**（C.35：708.1 s；我这边 R40-A5：783.1 s）。
  选 A 等于把刚验过的购买逻辑整体下线、用一份新代码替换 —— 风险与收益不成比例。
- **否决 C**：两层同帧抢同一笔资源（典型：IP 既买 ID 又买 IU），冲突不可观测。
- **选 B**：谁动的手永远确定。执行层调的是**同一个模块自己的公开方法**
  （同一条购买路径、同样的成本检查、同样的幂等性），不是另一套购买实现。
  冲突在面板「④ 正在执行」一栏可见。

「本帧无动作」的判据（保守）：模块 `tick()` 返回的动作摘要**连续 3 帧全空**才接管，
同 source 两次接管至少间隔 250 ms。宁可晚 3 帧，也不和模块抢同一笔钱。

## 3. verb 映射表：31 条全部登记，15 可代劳 / 14 归模块 / 2 原版无入口

spec 里 8 个策略合计 **31 个 verb**（去重后），一个不漏。

| policy | 条数 | 含义 |
|---|---:|---|
| `owned` | 15 | 执行层可代劳，调阶段模块自己的方法 |
| `delegated` | 14 | 归模块独占，执行层只显示不动手 |
| `unsupported` | 2 | 原版没有这个入口，面板写原因，不编动作 |

`owned` 15 条：routine 8（买维度/计数频率/维度提升/星系/献祭/重开/升级/大坍缩）、
early 2（无限维度、无限升级）、eternity 2（时间之理、永恒重置）、reality 3（现实升级、符文、现实重置）。

`delegated` 14 条，逐条都有理由，不是「懒得做」：

| verb | 为什么不动手 |
|---|---|
| `challengeSpecificOrder` / `buyAllowedOnly` / `crunchWhenDone` | 挑战规则由 `oreki-instant-challenges.js` 与 `OrekiEternityAutomation` 逐条处理 |
| `runChallengeIfRewardBlocks` | 同上（`buyEcStudiesAndStart`） |
| `buyTimeStudy` / `buyDilationStudy` | 模块把研究购买节流在 `_frame % 30`（`oreki-eternity-automation.js:735`），方法本身无内置节流。代劳等于把 30 帧节流换成 250 ms，**购买节奏会偏离已验证通关的那条路径** |
| `celestialSpecificOrder` / `spendUnlockResource` / `advanceCelestialNav` | `OrekiCelestialAutomation.tick()` 内部按天神分派，代劳等于递归 |
| Pelle 5 条（末日循环 / keepAutobuyers / 拉满间隔 / 再末日 / 推到 1e1000） | `OrekiEndgameAutomation.driveDoomed()` 相位机独占（20 s 冷却、残迹停滞判据、先买后末日），插一手会打乱相位 |

`unsupported` 2 条：`buyEternityUpgrade`（原版没有永恒升级商店，里程碑自动生效）、
`buyRealityMachine`（RM 由现实重置产出，无购买入口）。

## 4. 手动优先：以「点击」为信号（启发式，已写明不是精确归因）

原版没有「这笔是谁买的」审计。做法：`document` 上 capture 监听 `click`/`pointerdown`，
命中 `#ui` 内、且不在 `.l-options-grid`（设置）与 `.c-oreki-tutorial`（教程）里 ⇒
`OrekiSmartStrategy.noteManualAction(当前 goalId)` ⇒ 该 goal 静默 60 s（`spec.manualOverride.holdSeconds`）。

- 范围放大只会让自动层**多等 60 秒**（安全方向），不会在玩家操作时抢买（危险方向）。
- 面板必须显示「你刚刚手动操作过，已暂停 N 秒（目标：xxx）」，**不许静默暂停**。
- 单测覆盖：hold 期间 4 帧连续调用，执行层 0 次动手，`executor.reason=manual-hold`。

## 6. 实测（真实浏览器，全新存档，默认速度）

### 6.1 执行层挂到活对象（不是「代码存在」）

150 s 跑 `r40s2-smoke.jsonl` 末条：

```
exOk=true   exReg=routine|early|eternity|reality   exErr=""
exActN=501  exTryN=501  exLast=equipBestGlyph@reality:0
exIdle={"routine":0,"early":0,"eternity":4,"reality":14}
smOk=true   smStage=reality  smStrat=realityPush  smGoal=unlock-celestials  smDeg=false  smErr=""
eErr=""     realities=10   ecTarget=9
```

`exActN=501 == exTryN=501` 是**真实**读数，不是 bug：那时执行层把每一次空转调用都记成了「动作」。
已修正为「`actionCount` 只算真的买到（`acted=true`），空转记 `attemptCount`」，
并在 `r40s2-smoke2` 复验（见 §6.3）。

### 6.2 一致性：执行层没有把阶段判定搞坏

同一跑里 `smStage=reality` 与 `player.realities=10`、`realityStudy=false` 自洽；
`smBlock=""`（未命中任何 blocker）；`eErr=""`（终局模块无异常）。

### 6.3 复验跑（120 s，`r40s2-smoke2` / `r40s2-smoke3`）

`smoke2` 暴露了一个**真实缺陷**（不是配置问题）：

```
exActN=39  exTryN=409  exLast=equipBestGlyph@reality:0
```

409 次尝试里 370 次都花在 `equipBestGlyph` 上 —— `realityPush` 的 priority 里它排第一，
而符文槽满时它恒定返回 0，于是**后面的 `buyRealityUpgrade` / `runReality` 一次都轮不到**（饿死）。

修法：没买到的 verb 冷却 2 s（`NOOP_COOLDOWN_MS`），把机会让给后面的 verb。`smoke3` 复验：

```
exActN=3  exTryN=102  exLast=equipBestGlyph@reality:0  （末条恰好轮到它）
出现过的 verb（113 条采样）：buyInfinityDimension / buyTimeTheorem / eternity /
                              equipBestGlyph / runReality / buyRealityUpgrade   ← 6 种，不再只转一个
最后 6 条：runReality → buyRealityUpgrade → runReality → equipBestGlyph → runReality → equipBestGlyph
```

同一跑里还修掉第二处真实缺陷：**缓存决策里的 `manualHold` 会过期不走**。
`evaluate()` 在 1 s 节流窗口内直接返回 `lastKnownGood`，而那是拍快照时的 hold；
`clearManualHolds()` 之后缓存仍在让路，面板的「已暂停 N 秒」也不动。
改为节流分支用 `withFreshHold()` 按当前 `manualHolds` 重算 hold（其余字段不动）。
单测里正是这条让「第 11 项 verb 轮换」一开始始终 `v1=null`。

两处修复后单测 **36/36**（新增第 11 项：恒失败的 verb 必须让位，两次挑出的 verb 不同）。

## 7. 顺带补齐 C.35 §7 的未知项之一：速度

C.35 §7 写着「是否全程 10000× 无法从数据判定，待 agent-a 确认」。现在有答案，但**分两层**：

- **静态层（已核实）**：`GAME_SPEED_DEFAULT = 10000`（`src/core/speed-config.js:32`）；
  探针从不调 `GameSpeed.set`（`grep` 零命中）；倍率存在 localStorage `oreki-game-speed`，
  而探针启动时 `localStorage.clear()`（`pelle-probe.mjs:190`）⇒ 开跑时必然是默认值。
- **动态层（这是 C.35 真正的风险点）**：**动态速度默认开启**（`DYN_*` 参数在
  `speed-config.js`，连续 4 s 无进度就 ×2 升档）。所以「全程 10000×」在旧数据里**不成立也不可证**。
  已给探针加 `spd`（`oreki-game-speed` 键值）与 `spdDyn` 两个逐秒字段：
  键为 `null` = 全程默认；非 `null` = 中途被改过/升过档。**今后每一跑都能实测回答这个问题。**

  已实测（120 s，111 条采样，`r40s2-smoke2`）：`spd` 与 `spdDyn` **全部为 `null`**
  ⇒ 这 120 s 内倍率是默认 10000×，动态控制器没有升档、也没有写过持久化键。
  这只覆盖前 120 s，**不能外推到 700 s+ 的长跑**（动态升档发生在「连续 4 s 无进度」时，
  前半段最容易满足）。

⇒ C.35 的正文建议改成「开跑为默认 10000×，动态升档见 `spd` 字段」，不要再写「全程 10000×」。

## 10. 遗留与风险

1. **未做 A/B 对照**：要量化执行层的净贡献，得跑「关执行层 / 开执行层」各一次长跑。
   当前证据只支持「不拖后腿」，不支持「有加速」。
2. **点击启发式**：误判方向是安全的（多等 60 s），但会让玩家觉得「自动化变慢了」。
   若以后有更准的信号（例如给原版购买入口加 hook），应替换掉 DOM 监听。
3. **`buyTimeStudy` / `buyDilationStudy` 刻意不代劳**：若以后模块去掉 30 帧节流，
   这两条可以改为 `owned`，但必须先重跑一次长跑确认节奏。
4. 面板在设置页，不在 HUD：想看「下一步」必须切到设置。是否要挪到主界面，等 team-lead 定。
