**结论（一句话）：run1 在采样口径 1000 ms / 固定 10000× 下，于 t = 915.8 s 把 `player.isGameEnd`

且 run1 比历史四次都慢 133～208 s，慢的位置已定位到两段，**原因属 [未知]**。

## 0. 采样口径与倍率（硬规则：任何秒数必须带口径）

* **倍率 [实测]**：958 条采样里 `factor` 与 `factorEff` 的**唯一取值都是 10000**，
  `dynOn` 全部 `false`、`dynRamps` 全部 `0`。日志 `[speed]` 行同时留有
  `{"set":{"ok":true,"value":10000},"dynBefore":true,"dynSet":false,"dynAfter":false}`。
  ⇒ **本轮全程 10000×，动态升档（10000→20000→…→100000）完全没有参与。**
  这一点必须写在 915.8 旁边，否则会被误读成「跑在 100000× 上还这么慢」。
* **采样间隔 [实测]**：相邻 `t` 差中位数 1.0 s，分布 1.0(524) / 1.1(295) / 1.2(56) / 1.3(37) …，
  最大 6.7 s（GC 或页面卡顿）。958 条覆盖 1043.6 s ⇒ 平均 1.09 s/条。
  ⇒ **翻转时刻的分辨率是 ±1.1 s，`915.8` 不是毫秒级精度。**
* **`t` 的定义 [实测]**：`t = (Date.now() - window.__r40a6T0)/1000`，`T0` 由页面内 10 ms 轮询钩子在
  `player` 对象出现那一刻打点（`r40a6-longrun.mjs:226-254`），不是 Node 端轮询时刻。
  日志 `[t0] 钩子打点比 Node 端早 1141 ms`；`createdAt→at = 37 ms`。
  ⇒ **915.8 s 是「player 出现」起的墙钟，不含前面 4.4 s 的 `goto` 冷启动。**
  若按「按下开始」的口径算，约 920 s。
* **采样负载 [实测]**：32 字段 / 次。作为对照，708.1 s 基线跑的 `r40s1-full.jsonl` 是 **76 字段 / 次**
  （见 §6.1）。⇒ **run1 的采样比 708.1 s 基线更轻，不是更重。** 这条否掉了「采样更密导致变慢」。

## 3. `brk` 在 t = 5.3 就为真、而 `realities = 0` —— 解释清楚了

这是本轮最容易被误判成「作弊」的一条。**结论：是 AD5 的一次性阶段奖励 + AD5b 自动按下
`breakInfinity()`，走的是游戏自身路径，与「真实通关」口径不冲突。**

### 3.1 数据长什么样 [实测]

| 行 | t | crunches | totAML | brk | realities |
|---|---|---|---|---|---|
| 1 | 1.2 | 0 | 47.4366 | false | 0 |
| 4 | 3.3 | 0 | 268.2154 | false | 0 |
| 5 | 4.3 | 0 | 268.2154 | false | 0 |
| **6** | **5.3** | **1** | **308.5325** | **true** | **0** |
| 7 | 6.4 | 0 | 12446.0835 | true | 0 |
| 8 | 7.4 | 74970 | 18756.659 | true | 0 |

关键：**`brk` 翻真的那一条，`crunches` 恰好从 0 变成 1**（`crunches` 采的是
`Currency.infinitiesTotal`），`totAML` 恰好停在 308（≈ 反物质被夹在 `1.797e308`）。

⇒ 顺序是：**先完成第一次无限（t≈5 s），再由闸门打开 Break**；不是「开局就先给了 Break」。

### 3.2 代码路径（逐行）[静态推导]

1. `src/game.js:211` 在游戏循环里调 `OrekiBreakInfinityGate.tryOpen()`。
2. `src/core/oreki-break-infinity-gate.js:62-84` `active()` 的前置条件：
   `!player.break` ✓ / `player.auto.autobuyersOn` ✓（本 MOD 默认开） / `PlayerProgress.infinityUnlocked()` ✓
   （= 已完成首次无限，对应 t≈5.3 的 `crunches=1`） / 非挑战 ✓ / `!Autobuyer.bigCrunch.hasMaxedInterval` ✓。
3. `:102-109` **B 段一次性补贴**：把 IP 补足到 `BREAK_INTERVAL_TOTAL_COST = 32767`
   （= 间隔 150000→100 的 15 级全额成本），`grantedThisSession` 保证**一次会话只发一次**，
   且 `!Pelle.isDoomed` 才发；发出后立刻被 A 段花掉。
4. `:111-120` **A 段间隔升级**：循环调 `bc.upgradeInterval(false)`——这是游戏自身的购买路径，
   真实扣 IP、不伪造 `interval`。
5. 循环结束后 `hasMaxedInterval` 变为 true（`guard<64` 上限内每级都真实扣 IP）。
6. `src/game.js:213-226` **AD5b**（函数 `tryOpenBreakInfinityGate` 在 `:210-230`）：`!player.break && autobuyersOn && hasMaxedInterval && !挑战 && !doomed`
   ⇒ 调 `breakInfinity()`（`game.js:94-97`，里面有 `player.break = !player.break`，所以必须带 `!player.break` 守卫）。
   原版**只有 UI 按钮**会调它（`components/ui-modes/prestige-header/BreakInfinityButton.js`）。

⇒ 第 2 步到第 6 步可以在**同一帧**内跑完，所以采样里看到的是一步到位：
`t=5.3 brk=true, realities=0`。中间态（IP 32767、interval 逐级降）落在两条采样之间，**采不到**。

### 3.3 为什么这不是「作弊」[静态推导]

* 补贴上限**恰好等于**拉满间隔的全部成本（32767），发完即被消耗，玩家余额回到原处；
* 间隔升级走的是游戏自己的 `upgradeInterval(false)`，真实扣 IP；
* 一次性、只在本会话、`!Pelle.isDoomed` 才发 —— **毁灭态只放行 A 段，不发补贴**
  （`:96-100`，这是 R40-A5 为提高「真实通关」纯度专门加的收紧）。
* 同一机制在三次历史跑里同样生效 [实测]：`r40s1-full` 的 `brk` 在 **t=4.1**、`r40a5-arm2` 在 **t=4.2**、
  `r40s3-attrib900` 在 **t=4.0**；三者的 `ivl`（大坍缩间隔）都在同一秒从 **150000** 变成 **100**，
  `bcMaxInt` 同时变 true，而 `realities` 仍为 0。
  其中 `r40s3-attrib900` 尤其干净，能直接看到那一跳：
  `t=3.0 brk=false ivl=150000` → `t=4.0 brk=true ivl=100 bcMaxInt=true realities=0`。
  ⇒ **不是本轮新增的加速，而是 AD5 从 R19 起就有的形态。**
  （`r40s3-tutorial-light` 的 10 字段采样没有 `ivl`/`bcMaxInt`，无法同样核对。）

**但有一点必须说清楚**：这一步是「一次性补贴」，不是「从零攒 IP」。
按 `oreki-break-infinity-gate.js:14-19` 的核算，未 Break 时每次坍缩固定 1 IP、需要 32767 IP，
纯挂机约 9 天 —— 换句话说，**如果没有 AD5 的这笔补贴，本轮 915.8 s 不可能发生**。
报告的「真实」指的是「没有伪造阶段标志、没有直接写 `player.isGameEnd`、没有跳过任何游戏内购买路径」，
不是「没有任何 MOD 补贴」。两者别混。

## 5. run2 到底发生了什么 —— 两条进程共用一个 tag，互相踩

### 5.1 证据链 [实测]

1. `r40a6-run2.jsonl` 的 `t` **不单调**：相邻差出现 `+69.6 / −68.6 / +69.7 / −69.5` 交替。
   按 20 s 阈值切分后，恰好得到**两条各自 0 逆序的单调轨**（534 + 530 = 1064，无剩余）。**这是两条独立会话。**
2. 跑分器本身是**单页单写**：`fs.appendFileSync(JSONL, …)` 在 `await page.evaluate()` 之后串行执行
   （`r40a6-longrun.mjs:363-416`）。**一个进程不可能产出交错时序。**
3. `r40a6-run2.log` 只有**一条**时间线（`[ 9s] [ 19s] … [ 608s]`），且它的 `[  73s]` 行
   `r=5 totAML=1339190110.0453` 对应轨0，`t0` 行 `totAML=37.6476` 对应 jsonl 行1。
   ⇒ **日志只属于轨0**；轨1 的日志被覆盖了（`log()` 每次都 `writeFileSync(LOG, 全文)`，后写者胜）。
4. 两条轨的 t0 相距约 65 s：轨0 的 `fresh=1793391663351`（04:21:03），
   轨1 末条 t=679.9 而 jsonl mtime 是 04:31:18 ⇒ 轨1 的 t0 ≈ 04:19:58。

⇒ **同一个 `r40a6-run2` tag 被启动了两次，第二次启动时 `writeFileSync(JSONL,"")` 把文件清空，
两个进程继续往同一个文件 append，于是交错。** [合理推断，证据是 5.1.1-5.1.4]

### 5.2 它是被中断，不是失败 [实测]

两份进程都在 04:31:18 前后（agent aborted 时刻）消失：日志**没有 `[summary]`、没有 `[fatal]`、
没有 `[dead]`**，最后一行是正常的 10 s 心跳 `[ 608s] …`。
`max=1800s` 远未到，`gameEnd` 也从未出现。
⇒ **run2 = 跑到一半被杀。不能拿它当「未通关」的证据。**

### 5.3 对结论的影响

* **本轮只有一轮完整数据**（run1）。「可复现」需要至少两轮完整且都翻真 —— **不满足**。
* run2 唯一的正向价值是 §4.2 那条「两条独立新档在 t≈70 s 处到达同一状态（差 0.14%）」，
  说明**早期轨迹是可复现的**；但这不能外推到末段。
* 反面价值更值得记：**同 tag 双进程会把数据写废**（这次两个进程共用了一个 jsonl，且互相覆盖 `.log`）。
  R40-S3 §4 已经写过「必须顺序跑」；这次还多踩了一条 —— **同名 tag 没有互斥保护**。
  以后长跑必须**一 tag 一进程，启动前检查同名进程 / 同名 jsonl 是否存在**。
  （两个 Edge 会不会互相拖慢这个具体问题，本次**没有测**，不下结论。）

**按「到达第 N 个现实」对齐（秒）：**

**末段三段拆解（秒）：**

| 跑 | 100 现实 | 进毁灭 | 进毁灭时 realities | 100现实→毁灭 | 毁灭→gameEnd | gameEnd |
|---|---|---|---|---|---|---|

**读法：**

1. **早段不慢，反而最快**：5 / 10 现实处 run1 比基线早 0.9 / 5.2 s。
   ⇒ 不是「起手慢」，也不是「倍率被吃掉」。
2. **从 30 现实起逐段拉开**：30→100 现实，run1 每现实 ~6.0–7.5 s，基线 ~4.9–6.6 s，
   累计 +118.8 s。**这是全额差距的 57%。**
3. **末段更悬殊**：run1 到 100 现实后**多刷了 5 个现实**（105 才进毁灭；其余三跑都是 100 就进了），
   100→毁灭花了 97.9 s，其余 23.1–30.0 s。**这一段单独 +68～75 s，占差距的 33%。**
4. **毁灭→gameEnd 只差 14 s**（60.0 vs 45.9），这一段基本一致，不是问题所在。
5. 第 3 点的机制是 [实测] 可定位的：run1 一直在等 **Laitela `laiTier` 7→8**。
   `laiTier` 7 在 725.8 s、8 在 818.3 s，**单级 92.5 s**；而 1→7 的平均是 36.3 s/级。
   期间现实数从 95 爬到 105（闲着也是闲着，就继续刷现实）。
   `laiTier 8` 到位后 37.5 s 进毁灭（818.3 → 855.8）。

### 6.3 三个候选原因，逐个判

**候选 A：采样更密 —— 否掉 [实测]**

task 里最先想到的是「run1 采样更密」。数据**完全不支持**：

* run1 = **32 字段 / 次，0.92 条/s**。
  708.1 s 基线 = **76 字段 / 次，0.99 条/s**；
  769 s 那跑（`r40s3-attrib900`）= **88 字段 / 次，0.99 条/s**。
  ⇒ **run1 是这五次里字段最少、密度最低的一次，却是最慢的一次。**
  88 字段跑 769 s、32 字段跑 915.8 s —— 如果字段数有用，方向应该反过来。
* R40-S3 §5.1 确实测到「重采样（25 字段 + 每帧多跑一次 `OrekiSmartStrategy.evaluate()` + DOM×2）
  到 100 现实 +37%」，但那个开销的大头是**采样器额外调 `evaluate()`**，
  而 `r40a6-longrun.mjs` 的 `SAMPLE()` **不调 `evaluate()`**，只读 32 个字段。

⇒ **「采样更密」解释不了这 207.7 s。这条假设可以从后续讨论里划掉。**
（注：这不是受控实验 —— 字段数与代码版本、随机性混在一起，所以只能说「没有任何数据支持字段数越多越慢」
这个方向，不能说「字段数不影响速度」。要证伪得单独做一次 9 字段 vs 32 字段的对照。）

**候选 B：代码变了 —— 只有部分解释力 [实测 + 静态推导]**

* 被测代码：run1 用 `a0299a8`（03:55）。在它之前，`src/` 最后一次功能提交是 **`30dbd9e`（01:59，
  执行层「同帧不抢」）**；02:31 之后到 03:55 之间**只有 docs 提交**（`5d3c63d`/`579aac9`/`2804323`/…/`a0299a8`）。
  ⇒ **run1 与 R40-S3 的两次跑（02:35–03:20 区间）在 `src/` 上是同一份代码。**
* 而 S3 的两次跑（`r40s3-attrib900` 769 s、`r40s3-tutorial-light` 721.5 s，同代码）
  与 run1 差 147–195 s。⇒ 代码版本**不能**解释 run1 相对 S3 的落后。
* 但代码版本**能**解释 708.1 → 783.1 → 915.8 这个大趋势的一部分：708.1 s 基线（`r40s1-full`）
  跑在 `7cdf5f6`（00:28 执行层落地）**之前**，`OrekiSmartExecutor.tick()`（每帧）+
  `OrekiSmartStrategy.evaluate()`（每帧调用、内部 1 s 节流）在 run1 里都在跑。
  这两者**每帧都在主循环里**，与采样无关。S3 §5.1 测过「每秒多跑一次 `evaluate()`」在 100 现实处值 +37%。
  ⇒ **[合理推断]** 执行层/策略层是**固定成本**，会把每一跑都拖慢；但它解释不了 run1 与 S3 之间的 147 s。

**候选 C：并行抢资源 —— 已排除 [实测]**

我一开始怀疑 run1 时间窗内有别的 Edge 在跑。核对时间戳：`r40a6-smoke7.jsonl` mtime **03:57:32**、
`smoke6.log` **03:55:12**、`smoke5.jsonl` **03:47:06**，全在 run1 起跑（**03:59:30**，`fresh=1793390370713`）
**之前**结束。run1 独占 03:59:30–04:16:55。⇒ **没有并行。这条假设也划掉。**

**候选 D：符文/莱特拉随机性 —— 未被否掉，也未被证明 [未知]**

* 同代码、同倍率下，S3 的两次跑（`r40s3-tutorial-light` 721.5 与 `r40s3-attrib900` 769）就差 47 s，
  S3 §开头写明「两个方向的差都比教程效应大，说明教程效应淹没在单跑噪声里」。
  ⇒ **单跑噪声至少 ±47 s 是已被实测记录的。**
* run1 与 S3 的差是 147–195 s，**约为已记录噪声的 3–4 倍**，超出噪声但未到「不可能」。
* 具体嫌疑点 [合理推断]：`laiTier 7→8` 的 92.5 s（其余级 ~36 s）。Laitela 层数依赖现实次数与
  符文/资源，单次跑出慢一级是可能的；但**没有任何一轮历史数据逐层采过 `laiTier`**（`r40s1-full`
  与 `r40a5-arm2` 都没有这个字段），**无法对照**。

⇒ **§6 的诚实结论：**
* 「慢在哪」**已定位 [实测]**：57% 在 30→100 现实的现实刷层，33% 在「100 现实 → 毁灭」这段，
  而这段的实际瓶颈是 `laiTier 7→8` 用掉 92.5 s 并顺带多刷 5 个现实。
* 「为什么慢」**未定位 [未知]**：采样密度、并行、代码版本三条都被数据排除或只够解释一部分；
  剩下符文/莱特拉随机性无法用现有数据证伪。
* **不能写「HEAD 代码把通关从 708 s 拖到 915 s」** —— 同代码的 S3 跑只要 721.5 / 769 s。
