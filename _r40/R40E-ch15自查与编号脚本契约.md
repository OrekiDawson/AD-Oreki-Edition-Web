## 三、奇点那段是不是「原版的资源消耗关系」

逐行对过 `perform()`（`singularity.js:259-275`）：

```js
perform() {
  if (!this.capIsReached || Pelle.isDoomed) return;   // 门槛：暗能量 ≥ cap
  Currency.darkEnergy.reset();                        // 消耗：暗能量清零
  Currency.singularities.add(this.singularitiesGained);// 产出：按 11^n 结算
}
```

- 门槛是 `capIsReached = Currency.darkEnergy.gte(cap)`，`cap = 200 × 10^n`；
- **是消耗关系**：冷凝把暗能量清零再发奇点，不是「达到就白送」；
- 奇点里程碑不重置：里程碑的 `isUnlocked` 只看 `Currency.singularities`（`:30-32`），
  而 `perform()` 只 reset 暗能量，不碰奇点，所以里程碑只增不减；
- `gainPerCapIncrease` 默认 11、可被 `improvedSingularityCap` 里程碑改写（`:222-224`）。

原稿这几条本来就写对了，本轮只补了「扩容上限 50」的出处与「里程碑不随冷凝重置」的依据。

## 五、章节自动编号脚本：契约 + dry-run

脚本：`scripts/renumber_tutorial_chapters.mjs`

### 契约

| 项 | 约定 |
|---|---|
| 输入 | `src/core/oreki-tutorial-data.json` 的 `chapters` 数组，**数组顺序即真值** |
| 触发 | 只有「数组长度/顺序与现有 `id` 不一致」时才产生改动。纯正文改动下是 no-op（实测已确认） |
| 输出 | ① 按位置重写 `id` 为 `ch00…chNN`；② 旧 id → 新 id 映射表；③ 跨章引用改写清单（位置 + 前 + 后） |
| 引用面 | `title/subtitle/stageGoal/entry/automation/challenges/done/next/note`、`steps[].text`、`buyOrder[]`、`traps[]`、`numbers[].label·value`、`table.head/rows`、`appendices[].body` |
| 改写规则 | 「第 N 章」里的 N 视为**旧编号**，按映射换新；单次扫描查表，不做链式替换 |
| 安全 | 默认 `--dry-run` 不写盘；`--apply` 才写；`--simulate-insert-after <id>` 仅演示、强制不写盘 |
| 不做 | 不碰 `gen_tutorial_module.mjs` 的 `checkReleaseGate` / `listDraftChapters` |
