所以 500 ms 采样看不到它；只有在**被 hold 压住**的那些周期里 DS6 才会被采样到（`ds6samples=44~63`）。【推断（静态支撑充分）】

⇒ 若一次都不冻结：13 次现实 × 24.4 s ≈ **317 s** 就能到 r=60（实测 446.5 s，差 **129 s**）。

### 2.4 W3：`holdRealityForV` 护栏①的过期时间戳死锁（**新发现，和我的改动无关**）

`oreki-celestial-automation.js:552-563`：

```js
if (!this._vHoldSinceMs) {
  this._vHoldSinceMs = now;                       // ← 第一帧置位并 return true
  if (!this._lastDilationStartOkMs) this._lastDilationStartOkMs = now;
  return true;
}
if (!active && now - this._lastDilationStartOkMs > 60000) {   // ← 第二帧立刻命中
  this._vHoldSinceMs = 0;
  return false;                                   // ← 每帧都重复「置位→释放」
}
```

`_lastDilationStartOkMs` 只在 `startDilatedEternity()` 真正成功时更新（`:420`、`:446`），**没有任何地方在失败时刷新它**。于是当上一段膨胀是 60 s 之前启动的、而当前 `player.dilation.active === false` 时，这个 getter 变成「每帧 true 一瞬、随即 false」，对外表现恒为 `false`。

而 `tickDilation()` 的第一道闸就是 `if (!this.holdReality) return false;`（`:429`）—— 买 DS1 的代码在它后面。**⇒ hold 要 DS1 才不会自杀，DS1 要 hold 才买得到。**

实测吻合：446.5 s `realities` 一达标（`_vFinishEligible()` 为真，`:477`），`holdR` 仍然整整 36 s 是 `false`、`dsB=000000`、`maxDTL=0`；直到 482.6 s 另一条来源（`OrekiDilationAutomation.hold` 的 60 s 冷却走完）把 hold 顶起来，DS1 才在 484.1 s 买到，maxDT 在 **0.4 s** 内从 0 冲到 1e180，V 在 484.5 s 解锁。

> 这条**不是** W2 的副产品：即使把冷却改成 0，只要 `_lastDilationStartOkMs` 过期且膨胀没在跑，`holdRealityForV` 依旧恒假。两者叠加才造成 36 s。

### 2.5 主 Agent 的两个提问

**Q1：「900 s 内 `Vunl=false` 是不是 `oreki-eternity-automation.js` 改动引入的回归？」**
**不是。** 依据：
- 本次 `fix1+fix2` 构建 **484.5 s 就解锁 V**（`r40a2-t1`），而 `fix2`（430 s 采样）之所以 `Vunl=false`，是因为**采样窗口在 V 之前就结束了**（430 < 484.5），不是没到。
- `r40a-fix`（1000 s，只有 fix1、**没有** `equipGlyphs` 修复）里 `Vunl` 全程 false，而 `realities` 938 s 已达 70 —— 这一段可以归因到 fix1 时期仍存在的「每轮真实现后 0.4~4 s 再来一次静默全量重置」（`R40A-Web-EC-根因.md` §8.2 的 3/8 次调用栈证据），静默重置会清 `thisReality.maxDT`，使 V 的 maxDT 判据永远抓不到。**但这是「归因合理推断」，不是逐帧证明**，且我手头没有 fix1-only + maxDT 采样的日志。
- 因此对「12 min」这个数字，我给出的判定是：**【实测】当前构建 V=484.5 s / IU15=496.6 s，没有 12 min 的 V；【实测】12 min 的位置在莱特拉阶段（§3.3）。**

**Q2：「V 与 IU15 的到达时间为何退化？」**
- V：**+76.9 s**（407.6 → 484.5）。分解【实测】：`realities=60` 从 362.6 s 拖到 446.5 s（**+83.9 s**，因为 139.4 s 的现实被压住），maxDT 竞态从 45.0 s 缩到 38.0 s（**-7.0 s**）。R40-A 的 EC 链提速（DS6 94 s → 25.1 s）已经抵掉了约一个现实的量，所以净退化只有 77 s。
- IU15：+87.0 s（409.6 → 496.6）。IU15 的前置是 `realities` 与 `amE`，**它排在 V 之后 10~12 s**，所以退化量 = V 的退化量 + 排队。**没有独立的 IU15 墙。**

### 3.2 为什么这是结构性的

- `game.js:1110`：只有 `Time.thisRealityRealTime.totalSeconds < 30` 的那次完成才 `difficultyTier++`。
- `game.js:1101` 完成后 `entropy = -1`；`reality.js:701` 现实重置把熵清 0。⇒ **一个现实最多升一级**。
- 熵速率 `entropyGainPerSecond = clamp((log10(AM)/2e7)^2, 0, 100)/200`（`laitela.js:82`），上限 **0.5/s ⇒ 最少 2 s 填满**。
- ⇒ **单级下界 = 现实间隔 + 2 s**；`OREKI_REALITY_INTERVAL_CELESTIAL_MS = 15000`（`oreki-reality-automation.js:36`）⇒ **8 级下界 ≈ 8 × 17 = 136 s**。

实测 158.3 s vs 下界 136 s ⇒ **只剩 22 s 可挤**。R39 那里每个 run 只占 8~14% 的采样（≈2~3 s），熵确实 2 s 就满，**`LAT_TIER_WINDOW_MS = 28000` 不是浪费**——它只是「保住现实别在结算前被重置」的上限，不是等待预算。**把 28 s 放宽/收紧都不会省时间**（这条直接否掉了任务书里的一个候选方案）。

### 3.3 当前构建的硬墙 W4：`LAT_RUN_MIN_AM_EXP = 1e10` 与 `LAT_RUN_ENTER_MAX_REAL_MS = 15000` **在时间轴上互斥**

**【实测】`r40a2-t1` 的 496.6~1499.5 s（1003 s，1945 个采样）：**

- `Laitela.isRunning === true` 的采样：**0 条**
- `difficultyTier`：**恒 0**
- **amE ≥ 1e10 的采样 20 条 —— 这 20 条的 `thisRealityRealTime` 全部 ≥ 24 s（24/24/25/26/27/27/28/28/28/31/36/39/39/40/47/51/52/63/82/83），没有一次 < 15 s**
- `holdReality` 占空比 57%，现实寿命最长 84 s（说明 `holdForLaitela` 确实在压，压也不解决问题）

**⇒ 门槛是够得着的（越了 14 次），但每次都踩在 `realMs ≥ 15 s` 那一侧**：`:383` `if (realMs >= LAT_RUN_ENTER_MAX_REAL_MS) return;` 直接放过这次机会；而 15 s 那一刻 amE 只有 1e8~1e9 量级（**实测**：496.6 s 之后 `amE` 有 294 个采样停在 1e9 档）。等下一次现实，amE 又从 1e1 重新爬。**两个常量互斥 ⇒ 必然 0 次 run。**

**【静态】而且熵速率根本不需要 1e10**：`laitela.js:82` 的 clamp 上限在 `log10(AM) ≥ 2e8` 就达到（`2e8/2e7 = 10`，平方后 100 = clamp 上限）⇒ **指数 2e8 已经是 0.5/s 满速**。`:61` 选的 1e10 比「满速点」高 **50 倍**，注释里「速率 = (amE/5e8)^2/200」用的是旧除数 5e8（实际 `OREKI_LAITELA_ENTROPY_DIVISOR = 2e7`，`laitela.js:30`），阈值是按旧公式算的，缩放改了之后没有回算。
